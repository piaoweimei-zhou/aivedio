AI 短剧 / 视频创作者的端到端全栈生产工具：概念图 → 三视图 → 分镜 → 视频 → 剪辑 → 成片

后端：Python 3.12 + FastAPI 前端：React 18 + TS + AntD 5 AI：ComfyUI + 6 云端供应商 约 45 个后端模块 / 21 个阶段插件 / 7 个供应商插件 / 17 个前端页面

01 项目是什么

一套面向"短剧/视频创作者"的 AI 辅助生产工具，试图覆盖从创意到成片的全流程。

核心生产链路为：文本描述 → 概念图 → 精修/超分 → 三视图 / 360 全景 → 分镜 → 图生视频 → 视频剪辑 → 成片导出。围绕这条链路，集成了资产库管理、异步任务队列、无限画布（ComfyUI 节点编辑器）、多人分镜（MSR / 三元约束）、批量生成、模板系统等能力。

02 架构设计

设计上遵循明确的三层解耦，目标是对抗"线性管线"，走向"资产网络"。
Layer3 StageRegistry（阶段路由层）— 21 个 Stage 插件，声明输入/输出/供应商
Layer2 ProviderService（供应商抽象层）— 7 个供应商统一 generate 接口
Layer1 AssetService（资产注册表）— 类型系统 / 版本化 / 血缘追踪 / content_type
     │
  GenTaskManager 异步任务队列（并发控制 + 状态磁盘持久化 + WebSocket 进度）
  workflow_builder 工作流构建器（按内容类型自动选模板/尺寸/LoRA/触发词）

设计亮点

  • 资产网络而非线性管线：任意资产可进入"精修/三视图/分镜/提取"，非破坏性迭代，符合真实创作网状结构。
  • 插件化扩展：新增能力 = 注册一个新 Stage + 配一个新 Provider，无需改核心架构（已落到代码层面，非仅文档）。
  • 两级资产分类已落地：`asset_type`（生产阶段）+ `content_type`（角色/场景/道具）双维度，`stage_service` 已实现 `input_content_types` 校验，前端资产库也有二级筛选。
  • 内容类型驱动：角色/场景/道具自动切换不同工作流模板、宽高、LoRA 强度与触发词，属行业内较实用的自动参数策略。
  • 开源闭源结合：本地 ComfyUI 兜底 + 多个云端供应商，成本与质量的权衡空间灵活。

04 健康度实测结果

基于对本地源码的实际执行验证（非仅阅读）。
✔ 后端全部 Python 源码通过 py_compile 编译检查，无语法错误。
✘ import core 直接崩溃：core/__init__.py 导入了 exceptions / rate_limiter / retry_config / circuit_breaker / auth，但这些模块在磁盘上不存在。
⚠ canvas_service._broadcast() 通过 from core.ws_manager import get_ws_manager 做实时广播，会被上述崩溃 try/except 捕获并静默降级——画布变更的 WebSocket 实时推送实际上已失效，但没有任何报错提示。
⚠ 项目不是 git 仓库，无任何版本历史。所有演进只沉淀在文档和目录结构中，无法回滚、无法溯源、无法协作。

05 文档与代码的"版本代沟"

这是本仓库最突出的工程债：同一份代码存在多套彼此矛盾的描述，且引用了不存在的文件。
README.md（定义的是最早的六页面 MVP 蓝图）

描述 6 个前端页面、11 个阶段、4 个 API；实际前端已有 17 页、阶段 21 个、API 10+ 个。README 中列出的 pipeline_executor.py、video_service.py 在源码中不存在。

plan.md（asset_type / content_type 两级分类改造方案）

风险评估中多处引用 pipeline_executor.py（36 处引用）——该文件已被 workflow_builder / dag_executor / gen_task_manager 重构替代，方案基于的载体已不存在。好消息：方案要落地的 content_type 两级分类已在后端实现。

系统功能.md（较新的实际能力描述）

功能描述与现状较吻合，但同样引用了磁盘上不存在的 video_api.py / video_service.py（仅剩 __pycache__ 残留）。声称"17 个阶段"，磁盘实际 21 个。

顶层大量 .md 与 industrial 规划（ai_video.md / 优化集成.md / 工业化/ 等）

含 227KB 的《小工具方案.md》、商业差距/第三方建议/方案评估等，反映项目的商业化/工业化探索方向，但多数未能在代码中定位到对应实现，属于"规划层"。文档整体明显多于实现。

⚑ 治理建议：明确定位现状文档（系统功能.md）与目标规划（各 .md / 工业化），删除过时的 pipeline_executor 引用，避免新人以错误蓝图为准。

未走 gitignore 的数据混入工作区低data/、output/ 按 .gitignore 应被忽略，但当前无 git 托管，真实密钥/产物存在丢失与泄露隐患。

07 行动建议（按优先级）

修复 core/ 包，恢复画布实时广播

删除 core/__init__.py 中对不存在模块的 import，或将其指向真实存在的 services/ws_service.py；让 canvas_service._broadcast 重新工作并暴露真实错误。

建立 git 版本控制

初始化仓库，写入 .gitignore（已具备），提交现状作为基线快照，之后任何大改动都可回滚。

重建可复现的环境

在唯一 Python 版本下沉，用 pip freeze 生成精确 requirements.txt（或 requirements.lock），删除跨版本 __pycache__ 混乱。

拆分巨型单文件

优先拆 comfyui_service.py（执行/工作流/文件/进程管理已与 comfyui/ 目录重复）与 workflow_builder.py；前端拆 AssetsPage.tsx 为独立组件。

文档治理

将文档分级为"现状"与"规划"，清理对 pipeline_executor / video_service 的过时引用，让 README 反映真实结构。

密钥后移

废弃前端 localStorage 存 Key，改为后端 .env + 服务端鉴权下发。

08 方向洞察

从 工业化/ 目录与顶层规划看，项目正从"个人可用的工具"向"可批量产出的工业化管线"演进。
  • 已投入的工业化能力：CSV 批量分镜、多层/多人渲染、模板批量提取、模板清场+蒙版（SAM2）、三元约束与姿态优化——这些正是"从单张出图到按镜头/模板批量生产"的体现。
  • 尚未落地的商业化考量：商业差距 / 第三方建议 / 方案评估等文档说明团队在反复评估"生产流程 vs 商业价值"，但大多未形成代码实现。
  • 核心护城河判断：在 AI 出图/出视频在同质化的当下，真正的壁垒是把"内容类型→工作流/参数"的领域知识固化成系统自动化，而不是某个单独的生成步骤。
