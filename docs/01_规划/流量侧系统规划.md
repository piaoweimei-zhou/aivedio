> 版本：v1.4 ｜ 日期：2026-08-25 ｜ 状态：规划（待评审）

## 0. 一句话定位

**用内容矩阵为自己的产品与多变现渠道获客，兜底躺赚并行。**
Director 做内容生产，TrafficOS 做"3 类内容 × 7 种变现 × N 个账号"的**内容变现机器**。

**产品与变现承接面**（已有）：短视频去水印工具（第一个工具，可下载+分析）、192 个工具方向、虚拟资源、网课培训、SaaS 系统、商业变现子弹库。

## 1. 战略判断

| 判断 | 依据 |
|---|---|
| 生产能力已过剩 | director 一键成片跑通、bug 闭环——**生产逻辑无需再打磨** |
| 但需"薄契约门面" | 现有 API 是内部 DAG 步骤模型（batch 接口），**没有外部消费面**——须在 director 内加一层薄适配器（contract_api.py），包装现有服务。**这是唯一必要的生产侧投入**（非打磨生产逻辑，是加外部门面） |
| 变现不止"卖产品" | 兜底躺赚 = 广告分成 + 网盘拉新 + 闲鱼工具 + SaaS + 资源 + 网课 多轨并行 |
| 不同变现需要不同账号 | 广告分成要播放量、网盘拉新要资源吸引力、闲鱼要信任、SaaS 要专业——混在一个号会互相稀释 |
| 工具即传感器 | 去水印工具天然能"下载内容"→ 解析爆款 → 自动化拆解库 + 用户需求信号 → 反哺选题 |

**北极星指标**：`周总收益 = Σ(各账号内容曝光×点击×完播) × 各变现转化率 × 单价`

## 3. 账号矩阵规划（内容维度 × 变现目标）

账号是"内容维度 + 变现主目标"的组合，每个账号一个清晰人设：

| 账号 | 内容维度 | 变现主目标 | 发布节奏 | 人设 |
|---|---|---|---|---|
| 内容号 ×N | 纯内容（短剧/科普/热点） | 广告分成 | 高频（日更） | 泛娱乐/科普人设 |
| 资源号 ×N | 知识+资源展示 | 网盘拉新/虚拟资源 | 中频 | 资源分享者 |
| 工具号 ×N | 软广（场景段子/演示） | 闲鱼成交/下载 | 中频 | 工具使用者/极客 |
| 知识号 ×N | 知识讲解 | 网课/咨询 | 中频 | 专家人设 |
| 产品号 ×N | 软广+行业方案 | SaaS/产品 | 低频高质 | 品牌人设 |

**MVP 起步**：5 类账号各 1 个 = 5 账号验证（不批量违规，跑通再加）。

## 4. 工具即传感器（v1.2 核心新增）

**去水印工具不只是一个产品，还是流量系统的数据传感器**：

```
┌─────────────────────────────────────────────────┐
│  去水印工具（下载内容）                          │
│    ├─ 用户下载了什么内容 → 【需求信号】→ 选题   │
│    ├─ 下载内容可解析 → 【爆款拆解自动化】→ 拆解库│
│    └─ 用户行为漏斗 → 【人群画像】→ 内容调优      │
└─────────────────────────────────────────────────┘
```

| 能力 | 机制 | 价值 |
|---|---|---|
| 需求信号采集 | 工具记录用户下载内容的领域/关键词（脱敏聚合） | 直接告诉你"用户想要什么"→ 选题命中率↑ |
| 爆款拆解自动化 | 下载的内容可解析标题/封面/结构/文案/数据 | 自动填充爆款拆解库（替代手动录入） |
| 人群画像 | 下载行为 + 内容偏好聚合 | 内容调优 + 广告定向 |

**关键设计**：工具端上报**脱敏聚合数据**（领域/关键词热度，不采集个人信息），流量系统消费这些信号生成选题。

## 5. 系统架构（v1.3：双服务解耦）

### 5.1 总拓扑：两个独立服务 + 接口契约

```
┌───────────────────┐       ┌───────────────────┐       ┌──────────┐
│   TrafficOS       │       │   director        │       │  工具矩阵 │
│   (流量侧服务)     │  HTTP │   (生产侧服务)     │  HTTP  │  (传感器) │
│                   │ ────▶ │                   │ ◀────  │          │
│ 选题/账号/包装/   │  契约  │ 一键成片/批量/素材 │  信号  │ 去水印等  │
│ 发布/数据/变现     │       │  (生产逻辑零改动)   │ 上报   │          │
└───────────────────┘       └───────────────────┘       └──────────┘
       │                             ▲
       │  独立部署/独立售卖           │  独立部署/独立售卖
       └─────────────────────────────┘
       通过稳定的 OpenAPI 接口契约对接（可合可分）
```

### 5.2 核心决策：接口契约解耦（回答"合/分"问题）

| 模式 | 做法 | 适用 |
|---|---|---|
| **合体用** | TrafficOS 调 director 生产 API，选题→一键送生产→产出回传，流程无缝 | 自用主流程 |
| **分开用** | director 独立卖（只做生产的人买）；TrafficOS 独立跑（规划/流量/数据） | 产品化/多用户 |
| **对接他方** | 任何满足"内容生产契约"的服务都能替换 director | 未来扩展 |

**关键——"零改动"的真实含义**：现状核实（2026-08-25）：
- director **没有** `/contract/*` router、**没有** API-key 鉴权中间件
- 现有 `POST /api/director/batches` 是**内部 DAG 步骤模型**（`stage_id + input_asset_ids + input_from_steps + provider_id`），**不是**"提交 Content Spec 得视频"的外部面

因此契约层必须**在 director 内新增**：`backend/api/contract_api.py`（薄适配器 + API Key 鉴权），**包装现有 batch/stage 服务，不改动任何生产逻辑**。准确表述：**"零改动生产逻辑 + 新增薄契约适配器"**。这是让解耦声明成立的必要前置。

### 5.3 内容生产契约（Production Contract）

TrafficOS 与 director 之间只认一份标准接口（OpenAPI 约定，单一事实源）：
- **契约文件**：`docs/01_规划/traffic_contract.openapi.yaml`（schema 以它为准）

| 接口 | 方向 | 作用 |
|---|---|---|
| `POST /contract/produce` | TrafficOS→director | 提交"内容规格"，创建生产任务（**幂等，按 content_id 去重**） |
| `GET /contract/produce/{task_id}` | TrafficOS→director | 查进度/状态/产物 URL/错误 |
| `POST /contract/produce/{task_id}/cancel` | TrafficOS→director | 取消任务（幂等） |
| `GET /contract/capabilities` | TrafficOS→director | 能力声明（支持哪些 stage/维度/参数） |
| `POST {callback_url}` | director→TrafficOS | 生产完成/失败回调（webhook） |

**status 枚举（契约唯一值）**：
```
queued → running → done | failed | cancelled
```

**错误 payload（回调/查询共用）**：
```json
{ "error_code": "STAGE_FAILED", "message": "xxx", "failed_step_id": "step_3" }
```

**内容规格（Content Spec）——跨系统唯一的数据载体**：
```json
{
  "content_id": "c_20260825_001",           // 幂等键，重复提交返回同一任务
  "dimension": "knowledge",                 // 枚举: pure_content/knowledge/soft_ad
  "monetizer": "course",                    // 枚举: adshare/netdisk/xianyu/saas/resource/course/tool
  "account_id": "acc_knowledge_01",
  "script": {                               // 对齐 director 真实可接收的 stage 输入
    "type": "video_script_mixin",           // 由 /contract/capabilities 声明支持的 type
    "acts": [{ "narration": "...", "duration_s": 5, "visual_hint": "..." }]
  },
  "assets": ["ref_img_url..."],             // 由 TrafficOS 提供公网可访问 URL
  "packaging": { "titles": [...], "cover_url": "...", "hook": "..." },  // 可选
  "params": { "resolution": "480p", "fps": 24, "duration_s": 5 },
  "callback_url": "https://traffic.example/api/traffic/produce-done",
  "traffic_meta": { "dimension": "knowledge", "monetizer": "course", "account_id": "acc_knowledge_01" }
}
```

**asset URL 生命周期（分离部署关键）**：
- director 产出的 asset URL 由 director 提供**签名 URL（TTL 可配，默认 24h）**，TrafficOS 在有效期内拉取
- 需要长期持有 → TrafficOS **拷贝到自己存储**（contract 提供 `POST /contract/produce/{task_id}/assets/{asset_id}/claim` 标记已转存）

**script 对齐原则**：Content Spec 的 `script` 字段**不是发明新模型**，而是**引用 director 的 stage/stage-input 形状**——以 `/contract/capabilities` 返回的 `supported_stage_types` 为准。TrafficOS 端先拉 capabilities 再构造 spec。

生产完成回传：`{content_id, task_id, status, assets:[{asset_id,type,url,ttl_sec}], traffic_meta}`

### 5.3.1 幂等与失败语义

| 规则 | 定义 |
|---|---|
| 幂等 | `POST /contract/produce` 以 `content_id` 去重：重复提交返回已有任务 + `"duplicate": true`，不重复生产 |
| 取消 | `POST /cancel` 幂等；仅 `queued/running` 可取消；取消后状态终态 `cancelled` |
| 失败 | 失败即终态，带 `error_code + message`；重试 = 新 `content_id`（或 TrafficOS 显式 `retry: true`） |
| 回调 | 终态（done/failed/cancelled）触发一次回调；回调失败由 director 重试 3 次（退避 1s/10s/60s），仍失败则 TrafficOS 轮询兜底 |

### 5.4 数据归属与引用

| 数据 | 归属 | 说明 |
|---|---|---|
| 选题/账号/包装/发布/数据/变现 | **TrafficOS 库** | 独立，不依赖 director |
| 素材/产物/项目/工作流 | **director 库** | 保持现状 |
| 关联键 | `content_id` / `asset_id` | 跨系统引用，双向可查 |

**不共享数据库**，只共享契约——这是"可分"的根基。

### 5.5 部署形态

| 形态 | 说明 |
|---|---|
| 同机双端口 | TrafficOS:8001 + director:8000，本地开发/自用 |
| 分离部署 | 各自服务器/容器，配置 `director_base_url` 即可对接 |
| 单进程合体 | 可选（后期），通过 `include_router` 挂载，但**不推荐默认**（保解耦） |

TrafficOS 配置项：`DIRECTOR_BASE_URL`（生产侧地址）+ `DIRECTOR_API_KEY`（鉴权）。

### 5.6 鉴权与安全

- TrafficOS→director：API Key（`X-API-Key` header），由 **contract_api.py 内实现依赖校验**（现状无任何鉴权中间件，属契约层新增，不碰生产逻辑）
- 工具→TrafficOS：脱敏信号 + API Key
- 不暴露内部库，只走契约接口
- 密钥配置：director 侧 `CONTRACT_API_KEY`（env）；分离部署时 TrafficOS 配置 `DIRECTOR_API_KEY`

## 6. 模块详设（v1.3 增量）

### 6.1 ⓞ 内容战略层
- 维度定义（纯内容/知识/软广）+ **变现目标绑定**（每条内容可选 1 个变现动作）
- 账号矩阵：账号 ↔ 维度 ↔ 变现目标 ↔ 人设 ↔ 节奏 配置化
- 配比管理：按账号/变现目标排产

### 6.2 ⓢ 工具传感器
- `POST /api/traffic/signals`：工具端上报脱敏需求信号（领域/关键词/热度）
- 爆款自动拆解：工具下载内容 → 解析元数据 → 写入拆解库
- 人群画像：行为聚合，输出到选题打分

### 6.3 ① 选题层（升级：变现权重）
```
score = w1×热度 + w2×(1-竞争) + w3×契合 + w4×时效
        + w5×转化价值(变现目标贡献) + w6×需求信号(来自工具)
```
- 爆款拆解库：半自动（工具采集）+ 手动补充
- 选题来源：热点 + 子弹库卖点 + **工具需求信号** + 用户问题

### 6.4 ③ 包装层
- 标题/封面/钩子按 **维度 + 账号人设 + 变现目标** 三轴生成
- 例：资源号用"XX 全套资源，转存就送"；工具号用"3 秒去水印，亲测可用"

### 6.5 ④ 发布层
- 账号矩阵（5 类）+ 定时 + 审核 + 重试
- 各账号独立节奏（内容号日更 / 产品号低频）

### 6.6 ⑤ 数据层（升级：多变现转化）
| 指标类型 | 内容 |
|---|---|
| 流量 | 播放/完播/点赞/评论/转发/涨粉 |
| **变现** | 广告分成收益、网盘拉新数、闲鱼成交、SaaS 试用/付费、资源领取、课程报名、工具下载/激活 |
| 归因 | 每账号 ROI = 变现收益 / 内容投入，周报输出 |

### 6.7 ⑥ 迭代层
- 高 ROI 账号/维度/内容特征回灌 → 调配比和权重
- 广告分成号：追播放 → 提高纯内容权重；工具号：追成交 → 提高软广权重
- 内容日历（按账号 × 维度 × 变现）

## 13. 生产端灵活化（L1+L2 落地，2026-08-26）

### 13.1 问题（用户提出"生产端僵化"）

旧生产端只能跑"固定 4 个 20 秒片段 ≈ 30 分钟"，无法自由组合时长（5s/10s/15s/3min）与片段数，与 A 组契约无法顺畅衔接，测试成本高。

**调研结论——僵化不在后端引擎**：
- `dag_executor.py` / `batch_api.py`：任意 steps 列表 + 拓扑排序，**灵活**
- `video_stage` segmented 路径：`segment_prompts + segment_durations` 逐段生成拼接，**灵活**
- 僵化在三处上层构造器：前端 `OneClickVideoPage.tsx` preset 硬编码、`baseline_oneclick.py` 硬编码 7 步 4 段、`contract_api._build_steps_from_spec` 只做单 stage 映射

### 13.2 L1：契约层通用剧本展开器（核心，A 组 P0 实质）

**文件**：`backend/api/contract_api.py`
- `_build_steps_from_spec`：当 `script.type == "video_script_mixin"` 且 `script.acts[N]` 非空 → `_build_script_video_steps`
- 展开逻辑：每幕 `{narration, duration_s, visual_hint}` → video 步骤的
  - `segment_prompts`（visual_hint 优先，回落 narration）
  - `segment_durations`（duration_s，缺省 5.0）——**任意段数 × 任意时长，100% 来自契约输入，零硬编码**
  - `tts_texts`（narration）+ `segmented_oneclick=True`
- `params.export=True` → 追加 export 步骤（依赖 video）
- 兼容：非 video_script_mixin / 空 acts → 原单 step 逻辑不变
- **时长约束**：video_stage 强制 `segment_durations[i] ≥ 4.0s`（生成模型下限）
- 复用已验证的 segmented_oneclick 路径（不依赖 storyboard 帧，无需图片素材即可文生视频）

**验证**：`tests/test_contract_flexible.py` 12 用例全过（3 幕 5/10/15s、单幕 5s、混合 4/7/180、缺省 5s、tts 开关、export 追加、引用图、兼容、DAG 拓扑 2 层 video→export）

### 13.3 L2：基线工具参数化（测试便利 + 段数×时长自由组合）

**文件**：`backend/tools/baseline_oneclick.py`
- 新增 `_resolve_seg_config()`：五档优先级
  `seg_durations 显式列表 > total_seconds 均分 > target_seconds 自动拆段 > segments×seg_seconds > 默认 4 段动态估算`
- 新增 `_auto_split_segments()`：成片总时长自动拆段（每段 ≤15s，末段补差）
- `build_oneclick_steps` 新增 `segments` / `seg_seconds` / `seg_durations` / `total_seconds` / `target_seconds` / `max_seg` 参数
- CLI 新增：`--segments N`、`--seg-seconds`（默认 5s）、`--seg-durations "5,10,15,20"`、`--total-seconds N`、`--target-seconds "10,15,...,55"`（多档位一次测）、`--max-seg`
- 向后兼容：g2_regression 原调用（2 位置参数）不变

**核心策略（用户确认）**：段数 × 每段 5s 混排成片
- `--segments 1` = 1×5s = 5s 成片
- `--segments 4` = 4×5s = 20s 成片（默认 4 段）
- `--segments 5` = 5×5s = 25s 成片
- `--segments 3 --seg-seconds 10` = 3×10s = 30s
- 显式混合时长仍可用：`--seg-durations "5,10,15"`

**验证**：1~5 段×5s / 3段×10s / 混合3段 / target 10/15/20/55 自动拆段 / 默认 4 段故事兼容，全部正确

### 13.4 效果

TrafficOS 提交 `acts=[{duration_s:5},...,{duration_s:180}]` 即可生成任意组合成片；`python baseline_oneclick.py --segments 1 --seg-durations 5` 即可快速验证单条 5s，不再等固定 30 分钟。
