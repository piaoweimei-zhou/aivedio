### 2.2 实际 DAG 结构（模式 B，默认 3 素材）

```
Layer 0:  s1_concept(角色)   s2_concept(角色)   s0_concept(场景)
Layer 1:  s1_angle(三视图)   s2_angle(三视图)   s0_pano(全景图)     ← 可选，取决于 outputForm
Layer 2:  s_video（依赖全部上层输出 + 内嵌 TTS）
Layer 3:  s_subtitle（可选）→ s_hook（可选）→ s_export（可选）
```

- 证据：`OneClickVideoPage.tsx:1124-1226`（buildSteps 模式 B）、`:1028-1088`（buildPostStages）
- 模式 A（分镜图直接输入）：仅 `s_video` + 后处理，证据 `OneClickVideoPage.tsx:1099-1122`

### 2.3 关键推论

1. **"一键成片"实际是"多素材生成长视频"，不是"主题→剧本→成片"全链路**。剧本生成是旁路（前端独立调用），不进 DAG。
2. **storyboard 环节被绕过**：模式 B 用 concept 图直接生成视频，缺少"分镜"这一质量环节；模式 A 依赖用户已有分镜图。
3. **TTS 与剪辑内嵌在 video 步骤**：意味着 video 步骤是单点故障——它失败则 TTS/剪辑全丢；且 TTS 失败是**静默降级**（见 §4.1）。

## 四、可靠性四支柱核查

### 4.1 失败重试 —— ⚠️ 框架存在，默认关闭

**代码事实**：
- `dag_executor.py:335-422` `_run_single_step` 有**完整重试循环**：`for attempt in range(max_retries + 1)`（L357）、超时/异常/业务失败均捕获（L363-405）、重试间隔 `RETRY_DELAY_SECS`（L41，默认 1.0s 固定间隔，**非指数退避**）
- `max_retries` 从 step 读取：`dag_executor.py:346`
- 但 `BatchStep.max_retries` 默认 0（`batch_task_service.py:60`），API 请求模型默认 0（`batch_api.py:40`），创建时透传默认 0（`batch_task_service.py:235`）
- **前端一键成片 `buildSteps` 未设置 `max_retries`** → 一键成片 DAG 实际零重试（`OneClickVideoPage.tsx:1093-1227` 无 max_retries 字段）
- ComfyUI 层另有 `_queue_prompt_with_retry`（`comfyui_video.py:363`、`comfyui_tts.py:108` 等）——这是**队列提交层**重试，非业务重试，不改变"一键成片零业务重试"的结论

**修正预设**：预设称"dag_executor 无执行逻辑、BatchStep.retry 字段空置"。实际：**执行逻辑完整、重试框架已写好，但默认关闭且前端不开启**。Phase 0 的重试工作不是"从零建"，而是"接通 + 默认开启 + 区分可重试/不可重试错误"。

### 4.2 断点续跑 —— ✅ 已具备「跳过已完成层 + 失败节点重跑」双向能力（修正原偏保守结论）

- `dag_executor.py:216-224` 收集 `status == "completed"` 的步骤，`:240-244` 跳过已完成层（断点续跑基础）
- 失败后提示"可重新 start() 断点续跑"：`batch_task_service.py:602-607`
- **`retry()` 已支持从失败步骤重置并重跑**（`batch_task_service.py:675-707`），且已暴露为 HTTP 接口 `POST /api/director/batches/{id}/retry`（`batch_api.py:169-176`）——**失败节点可经接口主动重跑，并非"只能手动重新 start 全部"**
- **修正原结论**：原报告称"断点续跑 = 仅跳过已完成层、失败需手动 retry()/重新 start、无自动重跑"，该表述偏保守。实际 `retry()` + `POST /{id}/retry` 已能精准重跑失败节点（含单步 reset 后重跑），缺口仅在**自动重跑触发**与**重启后自动恢复**（当前重启后 running→failed，`batch_task_service.py:183-187`，需人工介入或外部调度拉起 `retry()`）

### 4.3 结构化指标 —— ❌ 零实现（与预设一致）

- 全代码库 grep `metric|metrics|prometheus|成功率|成本统计`：**无任何统一指标体系**
- 仅有：结构化日志（`services/structured_logging.py`）+ 各阶段日志里的 `elapsed_ms`（如 `stage_service.py:487-488`、`dag_executor.py:372-374`）
- **缺口**：无每阶段成功率/耗时/成本/错误码聚合，无法回答"真实成功率是多少"

### 4.4 敏感词过滤 —— ❌ 全代码库零实现（与预设一致）

- grep `sensitive|敏感词|违禁|审核|blocklist|badword`：**零命中**
- 一键成片无任何发布前内容检查

## 六、成功率基线估算模型

### 6.1 为什么无法给出真实数字

静态审计能确认"各环节是否真连供应商"，但**无法确认成功率**——系统无指标、无重试、无全链路测试，历史上没有可复用的成功率数据。任何具体数字都是假设。

### 6.2 估算模型（供实测设计参考）

全链路成功率 ≈ 各环节成功率乘积（假设独立，且无重试时）：

```
P(全链路) = P(concept)^N × P(angle|pano)^N × P(video) × P(TTS) × P(subtitle) × P(hook) × P(export)
```

以默认 3 素材（2 角色 + 1 场景，含 angle/pano）为例，代入假设值：

| 环节 | 假设成功率 | 说明 |
|---|---|---|
| concept ×3 | 90% | ComfyUI 文生图，本地单 GPU 串行 |
| angle ×2 + pano ×1 | 90% | ComfyUI 三视图/全景 |
| video | 80% | 最重环节（90 分钟超时、分段+拼接、内嵌 TTS），单点故障 |
| TTS（内嵌） | 95% | 失败静默降级，不阻断 video |
| subtitle/hook/export | 98% | 本地 ffmpeg，稳定 |

**估算：0.9³ × 0.9³ × 0.8 × 0.95 × 0.98³ ≈ 0.47**（约 47%）

**推论**：
1. 无重试时，**video 环节是最大失效率来源**（假设 80%），且它一失败 TTS/剪辑全丢
2. 环节越多乘积越小——**环节数本身就在拉低成功率**，这是"全链路 9 环节"宣称 vs 实际 6-8 环节的差异点
3. 上述数字是假设，**必须实测校准**——这正是 Phase 0 第 0 步的意义

### 6.3 实测设计建议

- 复用 `_selftest_runner.py` 的 HTTP 驱动模式，但改为**真实成功路径**：配置好 ComfyUI + provider key 后，跑 N 次（建议 ≥10）一键成片
- 每环节记录：成功/失败、耗时、错误码、失败原因分类（超时/供应商限流/参数错误/本地 ffmpeg 失败）
- 产出：每环节成功率基线表 + 失败原因分布（Pareto），用于决定重试策略与质量门禁阈值

## 七、Phase 0 校准建议

### 7.1 修正后的 Phase 0 起点

| 项 | 原计划（../01_规划/商业化追赶计划.md） | 校准后 |
|---|---|---|
| 失败自动重试 | "从零建" | **接通 + 默认开启**：dag_executor 重试框架已存在，需 ① 前端一键成片传 `max_retries`（建议 2-3）② 区分可重试/不可重试错误 ③ 重试间隔改指数退避（当前固定 1s） |
| 断点续跑 | 补"从失败阶段恢复" | 已有跳过已完成层 + retry()；需补"失败步骤自动重跑"与"重启后自动恢复"（当前重启后 running→failed） |
| 结构化指标 | 从零建 | 从零建，但**先定指标口径**（每环节成功率/耗时/成本/错误码），再埋点 |
| 敏感词过滤 | 从零建 | 从零建，与预设一致 |
| **新增：基线测量** | 无 | **Phase 0 第 0 步**：先跑真实成功率基线（§6.3），再决定重试阈值与门禁阈值 |

### 7.2 建议的 Phase 0 执行顺序

1. **第 0 步（1-2 天）**：写"真实成功路径"基线测量脚本（复用 _selftest_runner 的 HTTP 驱动），跑 ≥10 次一键成片，产出每环节成功率基线表
2. **第 1 步（2-3 天）**：接通重试（前端传 max_retries + 后端区分错误类型 + 指数退避），**用基线数据验证重试后成功率提升**
3. **第 2 步（2-3 天）**：指标埋点（每环节成功率/耗时/成本/错误码聚合），**让基线测量可持续**
4. **第 3 步（2-3 天）**：敏感词过滤 + 平台规则预检
5. **第 4 步（1-2 天）**：断点续跑增强（失败步骤自动重跑、重启自动恢复）

**总工期约 2-3 周，与 Phase 0 原计划一致，但起点从"建重试"改为"先测量"**——避免在不知道真实失效率的情况下盲目设计重试策略。
